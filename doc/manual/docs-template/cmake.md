# CMake Integration

BTstack provides CMake helpers for adding the source groups your application
needs to an existing build. Your project chooses its toolchain, controller,
board support, and application target.

## Adding BTstack to an existing CMake project

Use `btstack_add_library` when your project already owns its application target.
For example, a project building an LE GATT server can start with:

```cmake
set(BTSTACK_ROOT "${CMAKE_CURRENT_LIST_DIR}/third_party/btstack")
include("${BTSTACK_ROOT}/tool/cmake/BTstack.cmake")

btstack_add_library(my_btstack
    CONFIG "${CMAKE_CURRENT_LIST_DIR}/config/btstack_config.h"
    GROUPS gatt-server transport-h4 platform-posix-run-loop)
target_link_libraries(my_application PRIVATE my_btstack)
```

This is a starting point: the project must select the remaining groups and
provide a suitable `btstack_config.h`. For a complete, buildable example, see
`port/posix-h4/gatt-counter-standalone`, including its README and POSIX H4
controller setup.

The helper resolves group dependencies, creates a static library, and supplies
BTstack's public and group-specific include directories. The configuration
header directory is propagated to consumers. Select the transport, run loop,
storage, chipset, and any other groups appropriate for your board; provide
board-local and SDK sources in your own targets.

The helper checks that the effective configuration defines the `ENABLE_*`
macros required by the selected groups. If the header depends on extra
preprocessor definitions or include paths, provide `CONFIG_DEFINITIONS` and
`CONFIG_INCLUDE_DIRECTORIES`. These are used both for the check and for the
library and its consumers. Configuration extraction runs at configure time
using the C compiler; target-specific compiler flags and generator expressions
are not applied to that check. Use the lower-level helpers if your SDK requires
such settings to preprocess the configuration correctly.

After configuration, inspect the library without building the application:

```sh
cmake --build build --target library-info
```

The output lists the requested and resolved groups, required and detected
configuration macros, and the library target's sources and include paths.
When a project creates more than one library with `btstack_add_library`, select
one with `LIBRARY=my_btstack cmake --build build --target library-info`.
The target properties reflect configuration-time changes made after the helper
call. They do not include application sources or all transitive usage
requirements from linked targets. With a multi-configuration generator, pass
`--config` to inspect the desired configuration.

For more control, `btstack_resolve_groups` and the `btstack_collect_sources`,
`btstack_collect_include_directories`, `btstack_collect_consumer_include_directories`,
and `btstack_collect_public_include_directories` helpers can be used to compose
your own target. `btstack_target_warnings` can optionally apply BTstack's
warning policy to that target. The convenience library does not impose a
warning policy on the project or suppress warnings in third-party sources.


## Source groups and resolver


`tool/cmake/BTstackSources.cmake` is the checked-in source catalog. It assigns
BTstack, selected platform, chipset, and third-party C files to lower-case,
hyphenated source groups such as `core`, `ble`, `gatt-server`,
`classic-rfcomm`, `transport-h4`, and `platform-posix-run-loop`.

The catalog also records private include directories used to compile each
group and consumer include directories for groups that expose application
headers. It is generated by `tool/create_cmake_sources.py`. Source groups
describe source ownership; the project selects its run loop, HCI transport,
storage, controller chipset, SDK sources, and board-support files.

### Finding groups

From the BTstack repository root, list the available groups or filter by part
of a name (case-insensitively):

```sh
python3 tool/btstack_groups.py list
python3 tool/btstack_groups.py list --filter run-loop
```

Inspect a group without configuring a port or a project:

```sh
python3 tool/btstack_groups.py info gatt-server
```

The detail command reports the group's direct dependencies, resolved group
closure, required configuration macros, owned sources, and consumer include
directories. Common groups also have short descriptions. Sources are relative
to the BTstack root; consumer include directories are absolute. Direct
dependencies can include internal configuration markers, which do not appear
in the selectable group list or resolved source closure.
Run `python3 tool/btstack_groups.py --help` for command usage. The wrapper
requires CMake on `PATH` and can be called from any working directory.


### Resolving dependencies

On top of the source groups, the handwritten `tool/cmake/BTstack.cmake` resolver 
supplies the knowledge over the inherent dependencies in the source catalog.
For example, `gatt-server` adds ATT database, ATT dispatch, and LE support; a Classic
profile can add RFCOMM, SDP, and its other lower layers.

The function `btstack_resolve_groups` returns the complete list of source groups
for the provided list of requested source groups. It is also aware of which 
BTstack configuration macros such as `ENABLE_BLE` or `ENABLE_CLASSIC` are required
for each source group.

## Port authoring

Ports can declare applications and capabilities to build several examples for
the same board. A project building one application can use the simpler workflow
above without these declarations.

### Port baseline

A port maintains a baseline set of groups required for its `main.c`,
the port-specific `btstack_config` and board setup.
Typical baseline groups include a run loop, HCI transport, persistent-storage
implementation, chipset support, and common cryptography. They are supplied
to every application built by that port.

Port-local files are separate from catalog groups. Examples include a board's
`main.c`, UART driver glue, generated controller firmware, and SDK sources.
Keeping these explicit makes it clear which files are reusable BTstack code and
which are specific to the custom project.


### Applications and requirements

`example/requirements.cmake` declares the list of BTstack examples. 
A declaration records its application sources, optional GATT database, 
and `NEEDS` without creating a target or enabling a feature:

```cmake
btstack_declare_application(gatt_counter
    SOURCES gatt_counter.c
    GATT_DB gatt_counter.gatt
    NEEDS gatt-server ENABLE_LE_PERIPHERAL)
```

`NEEDS` entries can be source groups, BTstack configuration macros from
`btstack_config.h`, or port-provided capabilities. By listing relevant 
source groups, which often correspond to Bluetooth Profiles or Protocols,
the required sources are marked as needed for this particular application.
The same style can describe an application owned by another project. Relative
`SOURCES` and `GATT_DB` paths are resolved against the directory containing the
declaration; absolute paths are preserved. Access the resolved paths with
`btstack_get_application_property(output application SOURCES)` or `GATT_DB`.

Requirements are documentation and validation input; they
do not enable a BTstack feature for a specifc target.


### Configuration and capabilities

BTstack source selection must agree with the effective `btstack_config.h`.
Ports obtain the preprocessed macro set with
`btstack_collect_port_configuration_macros` and register it with
`btstack_set_port_configuration_macros`. The resolver can then skip groups and
examples that require disabled features.

```cmake
btstack_declare_port(my-port)
btstack_collect_port_configuration_macros(MY_PORT_MACROS
    CONFIG "${CMAKE_CURRENT_SOURCE_DIR}/btstack_config.h"
    DEFINITIONS ${MY_PORT_COMPILE_DEFINITIONS})
btstack_set_port_configuration_macros(my-port ${MY_PORT_MACROS})
```

Pass the same relevant definitions to `DEFINITIONS` that compilation receives;
this is important when a configuration header conditionally enables a feature.

A *capability* is different from a BTstack feature. It describes something a
port provides, such as `audio` or `led`. A port declares the concrete groups,
sources, and public headers behind it with `btstack_declare_port_capability`.

For example, a POSIX port declares `audio` only when CMake found the PortAudio library.
An application that needs audio is then not selected on a port without it.


## Building declared applications in a port

Ports that build multiple examples normally use a small per-application static
library. `btstack_add_application_library` resolves an application's
requirements, combines them with the port baseline, and compiles only that
closure. Common groups are compiled once per port and reused by all selected
applications, which must use the same compilation settings.

The port still owns the final executable and its board policy:

```cmake
include("${BTSTACK_ROOT}/example/requirements.cmake")
set(EXAMPLES ${btstack_declared_applications})
btstack_filter_applications_for_port(EXAMPLES
    PORT my-port
    CANDIDATES ${EXAMPLES})

foreach(EXAMPLE IN LISTS EXAMPLES)
    btstack_get_application_property(APPLICATION_SOURCES "${EXAMPLE}" SOURCES)
    btstack_get_application_property(APPLICATION_GATT_DB "${EXAMPLE}" GATT_DB)
    btstack_add_application_library(
        TARGET btstack_${EXAMPLE}_library
        PORT my-port
        APPLICATION ${EXAMPLE}
        BASE_GROUPS ${MY_PORT_BASE_GROUPS}
        PORT_SOURCES ${MY_PORT_SOURCES}
        PUBLIC_INCLUDE_DIRECTORIES ${BTSTACK_PUBLIC_INCLUDES}
        PRIVATE_INCLUDE_DIRECTORIES "${CMAKE_CURRENT_SOURCE_DIR}")

    set(SOURCES_EXAMPLE)
    foreach(SOURCE IN LISTS APPLICATION_SOURCES)
        list(APPEND SOURCES_EXAMPLE "${SOURCE}")
    endforeach()
    add_executable(${EXAMPLE} ${SOURCES_EXAMPLE})

    if(APPLICATION_GATT_DB)
        btstack_target_gatt(${EXAMPLE}
            "${APPLICATION_GATT_DB}")
    endif()
    btstack_target_warnings(${EXAMPLE} STRICT)
    target_link_libraries(${EXAMPLE} PRIVATE btstack_${EXAMPLE}_library)
endforeach()
```

Call `btstack_declare_port(my-port)` before filtering. Register configuration
macros and optional capabilities before the filter as well. The filter does
not issue warnings for examples a port deliberately cannot support; it simply
does not create their targets.

`btstack_target_gatt` runs the GATT compiler, adds the generated header to the
target include path, and tracks imported `.gatt` files through a depfile. A
port should call it only for an application declaration that has `GATT_DB`.


## Inspecting a port and an example

A port can add inspection targets after its normal application loop:

```cmake
btstack_add_info_targets(PORT my-port)
```

After configuring the port, the following targets provide a concise view of
the resolved build:

```sh
cmake --build build --target port-info
cmake --build build --target list-applications
APPLICATION=gatt_counter cmake --build build --target application-info
cmake --build build --target list-examples
EXAMPLE=gatt_counter cmake --build build --target example-info
cmake --build build --target group-graph
```

`port-info` prints the effective BTstack configuration macros and declared
port capabilities. `list-applications` lists the candidates for the port,
and `application-info` reports whether a named application is included.
The existing `list-examples` and `example-info` targets remain available for
BTstack's example workflows; `list-examples` groups the built-in examples by
radio requirements. If an application is excluded, `application-info` reports missing configuration macros or
port capabilities. If it is included, it prints the complete source-file and
include-directory lists used to build it.

`group-graph` writes `btstack-groups.dot` in the build directory and also
writes an SVG when Graphviz `dot` is available. It is useful when reviewing a
source-group dependency or adding a new group.


## Using example information outside CMake

`example-info` is also a bridge to environments that do not consume CMake,
including IAR Embedded Workbench or Keil uVision. 
Configure a representative BTstack port with
CMake, then request the application you want to reproduce:

```sh
EXAMPLE=gatt_counter cmake --build build --target example-info
```

Use the reported lists to create the IAR project:

1. Add every reported source file, including application files, BTstack groups,
   port-local files, and generated firmware source when present.
2. Add every reported include directory. Keep the port configuration directory
   containing `btstack_config.h` ahead of generic include paths.
3. Use the same preprocessor definitions, and
   board SDK libraries as the reference CMake port.
4. Reproduce generated artifacts: run `compile_gatt.py` for a declared GATT
   database and perform any controller firmware conversion or download step
   required by the selected port.

The output is a resolved snapshot for a specific port configuration, not an
IAR project generator. It intentionally exposes the exact inputs needed by a
different build system while leaving compiler flags, linker scripts, startup
code, SDK integration, and debugger settings under that environment's control.
