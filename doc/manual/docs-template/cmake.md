# CMake Integration

BTstack provides CMake helpers for composing a build from small, named source
groups. They are useful both for BTstack ports in this repository and for a
project that already has its own CMake build, SDK import, board support, or
application targets.

The helpers do not create a top-level project, choose a toolchain, or impose a
Bluetooth controller. All porta in this repository keep those decisions in their
own `port/<name>/CMakeLists.txt`. An embedded project can use the same helpers to
add only the BTstack implementation, platform adaptation, and profiles it
needs.


## Concepts


### Source groups

`tool/cmake/BTstackSources.cmake` is the checked-in source catalog. It assigns
BTstack, selected platform, chipset, and third-party C files to lower-case,
hyphenated source groups such as `core`, `ble`, `gatt-server`,
`classic-rfcomm`, `transport-h4`, and `platform-posix-run-loop`.

The catalog also records the private include directories required to compile a
the files in a group, and consumer include directories for groups that expose application
headers. It is generated by `tool/create_cmake_sources.py`; do not edit the
generated catalog directly.

Source groups describe source ownership, not a complete application. In
particular, an embedded project still needs to choose its run loop, 
HCI transport, storage implementation, controller chipset, SDK sources, and board-local
files.


### Resolver

The handwritten `tool/cmake/BTstack.cmake` resolver supplies the dependency
knowledge that does not belong in the source catalog. For example,
`gatt-server` adds ATT database, ATT dispatch, and LE support; a Classic
profile can add RFCOMM, SDP, and its other lower layers.

Use `btstack_resolve_groups` before collecting files. It returns the complete,
dependency-first group closure and removes duplicates. The resolver also knows
which groups require BTstack configuration macros such as `ENABLE_BLE` or
`ENABLE_CLASSIC`.

### Port baseline

A port has a baseline set of groups selected by its `main.c`, the port-specific
`btstack_config` and board setup.
Typical baseline groups include a run loop, HCI transport, persistent-storage
implementation, chipset support, and common cryptography. They are supplied
to every application built by that port.

Port-local files are separate from catalog groups. Examples include a board's
`main.c`, UART driver glue, generated controller firmware, and SDK sources.
Keeping these explicit makes it clear which files are reusable BTstack code and
which are specific to the embedded project.


### Applications and requirements

`example/requirements.cmake` declares the list of BTstack examples. 
A declaration records its application sources, optional GATT database, 
and `NEEDS` without creating a target or enabling a feature:

```cmake
btstack_declare_application(gatt_counter
    SOURCES gatt_counter.c
    GATT_DB gatt_counter.gatt
    NEEDS gatt-server ENABLE_LE_PERIPHERAL)
```

`NEEDS` entries can be source groups, BTstack configuration macros from
`btstack_config.h`, or port-provided capabilities. By listing relevant 
source groups, which often correspond to Bluetooth Profiles or Protocols,
the required sources are marked as needed for this particular application.
The same style can describe an application owned by another project. 

Requirements are documentation and validation input; they
do not enable a BTstack feature for a specifc target.


### Configuration and capabilities

BTstack source selection must agree with the effective `btstack_config.h`.
Ports obtain the preprocessed macro set with
`btstack_collect_port_configuration_macros` and register it with
`btstack_set_port_configuration_macros`. The resolver can then skip groups and
examples that require disabled features.

```cmake
btstack_declare_port(my-port)
btstack_collect_port_configuration_macros(MY_PORT_MACROS
    CONFIG "${CMAKE_CURRENT_SOURCE_DIR}/btstack_config.h"
    DEFINITIONS ${MY_PORT_COMPILE_DEFINITIONS})
btstack_set_port_configuration_macros(my-port ${MY_PORT_MACROS})
```

Pass the same relevant definitions to `DEFINITIONS` that compilation receives;
this is important when a configuration header conditionally enables a feature.

A *capability* is different from a BTstack feature. It describes something a
port provides, such as `audio` or `led`. A port declares the concrete groups,
sources, and public headers behind it with `btstack_declare_port_capability`.

For example, a POSIX port declares `audio` only when CMake found the PortAudio library.
An application that needs audio is then not selected on a port without it.


## Adding BTstack to an existing CMake project

The lower-level source collection helpers are the simplest integration when an
application already owns its targets. This example creates a static library
for an LE GATT server; the project must replace the transport and platform
groups with the appropriate choices for its board.

```cmake
set(BTSTACK_ROOT "${CMAKE_CURRENT_LIST_DIR}/third_party/btstack")
include("${BTSTACK_ROOT}/tool/cmake/BTstack.cmake")

set(BTSTACK_REQUESTED_GROUPS
    gatt-server
    le-device-db-tlv
    tlv-none
    transport-h4
    platform-posix-run-loop
    platform-posix-uart
    platform-posix-tlv)

btstack_resolve_groups(BTSTACK_GROUPS
    GROUPS ${BTSTACK_REQUESTED_GROUPS})
btstack_collect_sources(BTSTACK_SOURCES
    ROOT "${BTSTACK_ROOT}"
    GROUPS ${BTSTACK_GROUPS})
btstack_collect_include_directories(BTSTACK_PRIVATE_INCLUDES
    ROOT "${BTSTACK_ROOT}"
    GROUPS ${BTSTACK_GROUPS})
btstack_collect_consumer_include_directories(BTSTACK_CONSUMER_INCLUDES
    ROOT "${BTSTACK_ROOT}"
    GROUPS ${BTSTACK_GROUPS})
btstack_collect_public_include_directories(BTSTACK_PUBLIC_INCLUDES
    ROOT "${BTSTACK_ROOT}")

add_library(my_btstack STATIC ${BTSTACK_SOURCES}
    src/my_hci_transport.c
    src/my_board_main.c)
target_include_directories(my_btstack
    PRIVATE
        ${BTSTACK_PRIVATE_INCLUDES}
        "${CMAKE_CURRENT_LIST_DIR}/config"
    PUBLIC
        ${BTSTACK_PUBLIC_INCLUDES}
        ${BTSTACK_CONSUMER_INCLUDES})
target_link_libraries(my_application PRIVATE my_btstack)
```

The project supplies its own `btstack_config.h` in the `config` directory.
Its `ENABLE_*` definitions must match the requested groups. For example, the
GATT server above requires BLE support. A Classic profile also requires
`ENABLE_CLASSIC`; merely omitting Classic source files does not remove Classic
code from shared BTstack files.

Apply warning policy only to the targets that compile BTstack-owned code:

```cmake
btstack_target_warnings(my_btstack STRICT)
```

Third-party group sources are compiled with their warning diagnostics
suppressed by the scoped helper. When using the lower-level API above, an
embedded project can apply its own policy to vendored sources.


## Building declared applications in a port

Ports that build multiple examples normally use a small per-application static
library. `btstack_add_application_library` resolves an application's
requirements, combines them with the port baseline, and compiles only that
closure. With a group-object target prefix, common groups are compiled once and
reused by all selected applications.

The port still owns the final executable and its board policy:

```cmake
include("${BTSTACK_ROOT}/example/requirements.cmake")
set(EXAMPLES ${btstack_declared_examples})
btstack_filter_examples_for_port(EXAMPLES
    PORT my-port
    CANDIDATES ${EXAMPLES})

foreach(EXAMPLE IN LISTS EXAMPLES)
    btstack_add_application_library(
        TARGET btstack_${EXAMPLE}_library
        ROOT "${BTSTACK_ROOT}"
        PORT my-port
        APPLICATION ${EXAMPLE}
        GROUP_OBJECT_TARGET_PREFIX btstack_my_port
        BASE_GROUPS ${MY_PORT_BASE_GROUPS}
        PORT_SOURCES ${MY_PORT_SOURCES}
        PUBLIC_INCLUDE_DIRECTORIES ${BTSTACK_PUBLIC_INCLUDES}
        PRIVATE_INCLUDE_DIRECTORIES "${CMAKE_CURRENT_SOURCE_DIR}")

    set(SOURCES_EXAMPLE)
    foreach(SOURCE IN LISTS btstack_example_${EXAMPLE}_sources)
        list(APPEND SOURCES_EXAMPLE "${BTSTACK_ROOT}/example/${SOURCE}")
    endforeach()
    add_executable(${EXAMPLE} ${SOURCES_EXAMPLE})

    if(btstack_example_${EXAMPLE}_gatt_db)
        btstack_target_gatt(${EXAMPLE}
            "${BTSTACK_ROOT}/example/${btstack_example_${EXAMPLE}_gatt_db}")
    endif()
    btstack_target_warnings(${EXAMPLE} STRICT)
    target_link_libraries(${EXAMPLE} PRIVATE btstack_${EXAMPLE}_library)
endforeach()
```

Call `btstack_declare_port(my-port)` before filtering. Register configuration
macros and optional capabilities before the filter as well. The filter does
not issue warnings for examples a port deliberately cannot support; it simply
does not create their targets.

`btstack_target_gatt` runs the GATT compiler, adds the generated header to the
target include path, and tracks imported `.gatt` files through a depfile. A
port should call it only for an application declaration that has `GATT_DB`.


## Inspecting a port and an example

A port can add inspection targets after its normal application loop:

```cmake
btstack_add_info_targets(PORT my-port)
```

After configuring the port, the following targets provide a concise view of
the resolved build:

```sh
cmake --build build --target port-info
cmake --build build --target list-examples
EXAMPLE=gatt_counter cmake --build build --target example-info
cmake --build build --target group-graph
```

`port-info` prints the effective BTstack configuration macros and declared
port capabilities. `list-examples` groups declared applications by their radio
requirements. `example-info` reports whether the named application is included
for this port. If it is excluded, it reports missing configuration macros or
port capabilities. If it is included, it prints the complete source-file and
include-directory lists used to build it.

`group-graph` writes `btstack-groups.dot` in the build directory and also
writes an SVG when Graphviz `dot` is available. It is useful when reviewing a
source-group dependency or adding a new group.


## Using example information outside CMake

`example-info` is also a bridge to environments that do not consume CMake,
including IAR Embedded Workbench or Keil uVision. 
Configure a representative BTstack port with
CMake, then request the application you want to reproduce:

```sh
EXAMPLE=gatt_counter cmake --build build --target example-info
```

Use the reported lists to create the IAR project:

1. Add every reported source file, including application files, BTstack groups,
   port-local files, and generated firmware source when present.
2. Add every reported include directory. Keep the port configuration directory
   containing `btstack_config.h` ahead of generic include paths.
3. Use the same preprocessor definitions, and
   board SDK libraries as the reference CMake port.
4. Reproduce generated artifacts: run `compile_gatt.py` for a declared GATT
   database and perform any controller firmware conversion or download step
   required by the selected port.

The output is a resolved snapshot for a specific port configuration, not an
IAR project generator. It intentionally exposes the exact inputs needed by a
different build system while leaving compiler flags, linker scripts, startup
code, SDK integration, and debugger settings under that environment's control.
